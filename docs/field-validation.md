# 현장 검증 준비 — 담당자 인터뷰와 실제 업무 짝 비교

기준일: 2026-09-14 · **준비된 질문지와 빈 기록 양식**. 실제 인터뷰·업무 실험은 수행하지 않았고 연락도 발송하지 않았다. 조사 결과, 사용자 인용, 절감 수치를 만들어 넣지 않는다. 문제 가설은 [현재 주제](project-topic.md), 실제 모델 기술 평가는 [평가 문서](evaluation.md)와 구분한다.

## 1. 확인할 가설과 탐색 대상

우선 가설은 “성남 문화시설·지역기관 홍보 담당자가 공식 자료 확인·재작성·오류 검토에 반복 부담을 겪는다”이다. 담당자 3~5명의 최근 실제 홍보물 한 건을 중심으로 탐색하는 안을 준비한다. 이는 모집 완료 인원이나 통계적 대표 표본이 아니다. 한 기관·쉬운 과제에 편중되면 그대로 기록한다.

시민의 이해·참여 증가는 별도 가설이다. 이 인터뷰나 담당자 시간 비교로 입증하지 않는다. 대외 연락은 연락 대상·내용에 대한 명시적 권한을 확보한 사람이 진행한다. 현재 산출물은 연락 가능한 질문지이며 연락 실행을 포함하지 않는다.

## 2. 인터뷰 질문지

도입 안내: “최근 홍보물을 실제로 어떻게 만드셨는지 이해하려는 조사입니다. 서비스 평가보다 현재 작업을 먼저 듣겠습니다. 답하기 어려운 질문은 건너뛸 수 있고, 공개할 내용과 익명 인용 범위는 별도로 확인하겠습니다.” 기록·녹음·화면 공유와 공개 인용 허용 여부를 각각 기록한다. 이름·연락처·비공개 기관 문서는 공개 저장소에 넣지 않는다.

| 순서 | 질문 | 확인할 자료·후속 질문 |
| --- | --- | --- |
| 1 | 가장 최근 완성한 지역문화 홍보물 한 건을 골라 요청부터 전달까지 설명해 주세요. | 실제 산출물, 제작 시점, 대상 독자, 담당 역할 |
| 2 | 처음 받은 요청에는 무엇이 있었고 무엇을 추가로 정해야 했나요? | 목적·분량·독자·마감·필수 정보 |
| 3 | 어떤 자료를 어디서 찾았고, 어떤 도구로 정리했나요? | 공식·비공식 출처 구분, 기존 AI 사용 여부 |
| 4 | 찾기 어렵거나 서로 다른 내용이 나온 정보가 있었나요? 없었다면 없었다고 알려주세요. | 해당 원문·날짜, 어떻게 처리했는지 |
| 5 | 초안을 쓰고 확인하고 승인받는 각 단계에 얼마나 걸렸나요? | 기록으로 확인한 시간인지 회상 추정인지 분리 |
| 6 | 최근 작업에서 되돌아가 수정한 부분은 무엇이었나요? | 사실 오류·표현·형식·승인 의견 등 실제 수정 이유 |
| 7 | 사실이 맞는지 누가 무엇을 보고 확인하나요? 확인을 끝내는 기준은 무엇인가요? | 최종 승인자, 필요한 출처, 미확인 정보 처리 |
| 8 | 지금 방식에서 가장 번거로운 단계와 그대로 유지하고 싶은 단계는 무엇인가요? | 반복 부담 가설에 대한 반박도 기록 |
| 9 | 데모의 근거·수정 기록을 보고 판단하려면 어떤 정보가 더 필요하나요? | 먼저 fixture임을 밝히고 실제 작업 적용 지점 확인 |
| 10 | 이 도구가 추가되면 오히려 늘어날 검토나 어려움은 무엇인가요? | 사용 불가 이유, 자료·보안·승인·학습 부담 |
| 11 | 같은 종류의 실제 과제로 현재 방식과 비교할 수 있나요? | 가능 여부, 과제 조건, 별도 참여 의사. 동의로 간주하지 않음 |
| 12 | 제가 이해한 작업 흐름과 어려움 중 틀리거나 빠진 점이 있나요? | 요약을 확인받고 해석과 원문 발언 구분 |

“유용하겠습니까”라는 응답만으로 수요를 확정하지 않는다. 최근 사례가 없거나 공유할 수 없으면 그 한계를 기록한다. 과거 시간을 추정한 인터뷰 응답은 직접 측정한 실험 시간과 합치지 않는다.

## 4. 현재 업무와 서비스 사용의 짝 비교 절차

1. **실제 과제와 승인 기준을 먼저 정한다.** 담당자의 통상 업무 중 현재 지원하는 8개 장소·카드뉴스 형식에 해당하는 과제에서 난도가 비슷한 서로 다른 과제 A/B를 고른다. 해당 과제가 없으면 적합한 실험 과제를 임의로 실제 수요로 꾸미지 말고 범위 불일치를 기록한다. 자료 길이·주장 수·독자·산출물 분량과 품질 기준을 맞춘다. 동일 과제를 반복해 답을 기억하는 효과를 피한다. 과제 설명·허용 자료 스냅샷·시간 상한·승인 기준을 실행 전에 고정한다.
2. **조건과 순서를 배정한다.** 한 참여자가 현재 방식과 서비스 방식을 각각 한 번 수행한다. 참여자 사이에서 현재→서비스, 서비스→현재 순서를 교차하고 A/B의 방식 배정도 교차한다. 실제 배정과 변경 사유를 기록한다. 표본이 작거나 배정이 불균형하면 분석 한계로 남긴다.
3. **현재 도구를 보존한다.** 기존에 쓰던 AI·편집 도구까지 기록한다. 양쪽에 허용하는 자료 범위와 품질 기준을 맞춘다. 서비스 사용법 연습은 별도 과제로 제공하고 연습·설정 시간을 따로 기록한다. 일반 업무의 추가 학습·설정 부담을 숨기지 않는다.
4. **시작부터 승인 가능 판정까지 측정한다.** 탐색·작성·검토·도구 대기를 포함한다. 작업과 무관한 휴식만 별도 기록하여 제외한다. 승인되지 않은 실행은 종료까지의 경과 시간과 사유를 남기고 승인 시간은 비운다. 실패·보류·중단을 표본에서 삭제하지 않는다.
5. **사람이 결과를 대조한다.** 가능하면 제작자와 다른 검토자가 방식 이름을 가린 결과를 같은 기준으로 평가한다. 공식 원문으로 원자 사실을 분해해 지지·충돌·불충분을 판정하고, 불일치는 원문과 최종 결정 이유를 보존한다. 검토자와 가림 여부를 기록한다. 앱의 자동 검수나 로컬 승인만으로 현장 승인을 대신하지 않는다.
6. **근거와 원시값을 보존한다.** 두 실행은 같은 `pair_id`의 두 행으로 저장한다. 입력·원문·출력·수정·판정·버전 기록을 연결하고, 개별 짝의 변화·중앙값·범위·유효 짝 수와 전체 시도 수를 보고한다. 기술 비교의 baseline/agent 결과와 섞지 않는다.

실제 업무 효과를 주장하는 서비스 조건에는 live 실행 결과가 필요하다. 설정이 없으면 fixture로 사용성·절차를 연습할 수 있지만 `service_fixture_rehearsal`로 기록하고 실제 AI 업무 효과 분석에서 제외한다. 이 문서 준비 과정에서는 유료 API를 호출하지 않았다.

## 5. 빈 CSV와 기록 기준

[실제 업무 짝 비교 CSV](templates/field-workflow-pairs.csv)는 **열 이름만 있는 빈 파일**이다. 값이 없다는 것은 미측정이지 0이 아니다. 실제 관측 후에만 행을 추가한다. 각 열의 의미는 다음과 같다.

| 열 | 정의·입력 규칙 |
| --- | --- |
| `pair_id`, `participant_id`, `session_date` | 같은 참여자의 두 방식 비교 ID, 익명 참여자 ID, 실제 수행 날짜 |
| `period`, `method`, `task_id`, `matched_task_set` | 실제 수행 순서, `current_workflow` / `service_live` / `service_fixture_rehearsal`, 과제 ID, A/B 과제 쌍 ID |
| `assignment_note` | 순서·과제 배정 및 계획에서 바뀐 이유 |
| `brief_ref`, `source_snapshot_ref`, `approval_criteria_ref` | 고정한 입력 요청, 허용 자료 원문·해시, 사람의 승인 기준 기록 위치 |
| `existing_tools`, `allowed_tools` | 통상 사용 도구와 이번 수행에서 허용한 도구. 기존 AI도 명시 |
| `training_seconds`, `setup_seconds` | 본 과제 밖에서 측정한 사용법 연습과 설정 시간. 총 작업 시간과 별도 보고 |
| `time_limit_seconds`, `started_at`, `ended_at`, `excluded_pause_seconds` | 사전에 정한 상한, 시간대 포함 시작·종료 시각, 업무 외 휴식 시간 |
| `elapsed_seconds`, `search_seconds`, `compose_seconds`, `review_seconds`, `other_seconds` | 경과 시간은 종료−시작−제외 휴식. 나머지는 서로 겹치지 않는 단계별 시간이며 합계가 경과 시간과 일치. 도구 대기는 해당 단계에 포함하고 측정 불가하면 비움 |
| `approved`, `approval_ready_seconds` | 사람 판정 `yes` / `no` / `not_reviewed`. 승인 가능 판정까지 측정한 시간은 `yes`일 때만 기록. 앱 실행 시간으로 대체하지 않음 |
| `human_edit_count`, `human_edit_log_ref` | 첫 초안 이후 사람이 한 의미 단위 수정 건수와 전후 로그. 키 입력·저장 횟수는 아님. 양쪽에 같은 집계 규칙 적용 |
| `total_fact_count`, `contradicted_fact_count`, `insufficient_fact_count`, `unsupported_fact_count` | 검토한 원자 사실 전체 수와 충돌·불충분 수. 미지원 수는 충돌+불충분이며 사실 0개일 때 비율은 산출하지 않음. 순수 질문·상상은 분모 제외하되 그 안의 실제 사실은 포함 |
| `reviewer_id`, `review_blinded`, `human_review_ref` | 익명 검토자, 방식 가림 `yes` / `no`, 사람의 사실 판정·인용·승인 사유 기록 위치 |
| `run_id`, `model_id`, `prompt_version`, `review_rules_version` | 서비스 실행 재현 정보. 현재 방식에 없으면 비우고 해당 없음으로 설명. 기존 도구가 AI면 확인 가능한 모델도 기록 |
| `api_cost_usd_estimated`, `cost_evidence_ref` | 해당 과제의 모든 확인 가능한 API 추정 비용과 근거. 확인되지 않은 비용은 0으로 대체하지 않음. 구독·인건비는 별도 기록 |
| `output_ref`, `outcome`, `missing_or_limitations` | 결과 파일·버전 위치, `completed` / `needs_review` / `failed` / `cancelled` / `time_limit`, 누락 값의 이유·실패·조건 차이 |

승인 기준은 사실 근거, 운영정보 시점, 독자 적합성, 형식·출처·권리 표시를 포함해 담당자와 사전에 정한다. 사람이 편집한 대본·이미지 등도 수정 로그에 포함하고 유형을 남긴다. 두 방식 중 하나만 승인됐으면 둘의 시간을 나누어 절감률을 계산하지 않는다. 실패율·승인율은 전체 시도 수와 함께, 시간의 짝 비교는 비교 가능한 승인 짝과 제외 사유를 함께 보고한다.

현재는 로컬 서버·SQLite에서 작업한다. 기관 도입이나 인증된 승인 체계는 합의·구현되어 있지 않다. 현장 검증 완료는 표를 채웠다는 사실이 아니라, 실제 사례와 판단 근거가 연결되고 문제 가설의 지지·반박·미확인이 드러나는 상태를 뜻한다.
