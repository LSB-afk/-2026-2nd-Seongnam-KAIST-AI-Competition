# 모델 역할 프롬프트와 검수 계약

실행 지침의 원본은 [`src/lib/prompts.ts`](../../src/lib/prompts.ts)다. 문서를 수정해도 런타임 프롬프트가 바뀌지는 않는다. 프롬프트를 변경할 때 `PROMPT_VERSION`을 올리고, 사실 검수 기준이 달라지면 `REVIEW_RULES_VERSION`도 올린다.

현재 버전은 `2026-09-13.1`, 검수 규칙은 `atomic-evidence-2026-09-13.1`이다. 실행 메타데이터에는 두 버전을, 개별 호출에는 `/decision`, `/compose`, `/review` 또는 `/custom` 역할 접미사를 남긴다. 평가용 분류기는 `ATOMIC_REVIEW_RULES`를 재사용할 수 있다. 모든 역할에 `brief.placeId`와 등록 장소 자료를 전달하며 다른 장소의 사실·사진을 혼합하지 않도록 지시한다.

| 역할 | 입력과 책임 | 서버가 별도로 강제하는 조건 |
| --- | --- | --- |
| 총괄 판단 `DECISION_PROMPT` | 홍보 목표, 최신 검수, 검색 이력, 보호된 카드, 남은 예산으로 다음 도구 선택 | 현재 버전·현재 대상 ID, 검색의 구체적 query/targetClaimIds/missingInformation/reason, 비검색 행동의 search=null |
| 작성·부분 수정 `COMPOSE_PROMPT` | 청소년용 카드 4장, 대상 카드의 오류 수정, 사람 편집과 다른 카드 보존 | 전체 카드 구조, ID 연결, 호출 상한; 대상별 병합과 사람 편집 보호는 실행 계층이 담당 |
| 독립 검수 `REVIEW_PROMPT` | 작성자가 등록한 Claim과 분류를 그대로 믿지 않고 모든 제목·본문·대본의 사실을 재추출 | 12개 필드가 빠짐없이 한 번씩 존재하고 구간을 합친 원문이 완전히 같아야 함 |

공통 지침은 외부 문서와 사용자 목표를 자료로 취급한다. 출처에 들어 있는 명령이 모델 지침을 바꾸지 못하도록 하고, 비밀값이나 내부 사고과정을 반환하도록 요구하지 않는다.

수정 대상에 Claim ID만 지정하면 해당 원문 구간의 정확한 치환만 허용한다. 같은 카드의 다른 주장·근거·제목·순서를 바꾸거나, 주장을 추가·삭제·분할하려면 카드 ID를 명시한 결정이 필요하다. 담당자가 편집한 카드는 어느 범위에서도 자동 적용하지 않고 제안으로 남긴다.

## 원자 사실 검수

검수 결과의 `fields`는 각 카드의 `title`, `body`, `script`를 모두 포함한다. 각 필드의 `segments.text`를 합치면 공백과 문장부호까지 원문과 같아야 한다. 서버는 이 구간들의 누적 위치를 계산하여 start/end로 저장한다. 평가에 freshness 및 인용별 관계·이유도 보존한다. 사실 구간에는 원자 평가 하나가 연결되고, 순수한 질문·가정·제목 등에는 `nonfact`, `assessmentId:null`과 이유가 필요하다.

`2013년에 개관했고 월요일은 휴관한다`는 개관 시점과 휴관일을 나누어 평가한다. 첫 사실이 맞아도 두 번째가 반박되면 두 번째 평가와 전체 Claim의 지지 상태를 별도로 남긴다. 상상 카드의 `2015년에 개관한 박물관을 우주로 옮긴다면?`에서도 실제 개관 연도는 독립 사실이다.

| 판정 | 근거 조건 | 다음 조치 예 |
| --- | --- | --- |
| `supported` | 해당 사실 전체를 지지하는 실제 원문 인용 | `keep` |
| `contradicted` | 그 사실과 반대인 내용을 확인할 수 있는 원문 인용 | `revise`, `delete` |
| `insufficient` | 자료 없음, 무관한 인용, 불확실한 최신성, 해소되지 않은 충돌 | `search`, `human_review` |

운영시간·입장료·휴관일·공식 사업 등 현재 정보는 `freshness`를 별도로 판단한다. 오래되었거나 충돌하는 자료를 supported로 승인하지 않는다. 현재 정보의 코드 검사에서는 수정일→발행일→조회일 순으로 날짜를 확인하고, 초기 보수적 기준인 검수 시점 기준 366일 이내를 적용한다. 명시적으로 오래된 자료는 사람이 현재 유효성을 확인하거나 새 근거를 확보해야 한다. 해소되지 않은 충돌은 insufficient와 human_review로 남긴다. 미발견을 거짓의 증거로 취급하지 않는다.

각 평가의 인용에는 실제 `evidenceId`, `sourceId`, `quote`와 supports/contradicts/context 관계가 필요하다. 서버는 ID와 원문, 저장된 출처의 정확한 구간을 확인한다. 지지 판정의 수치가 인용에 없거나 근거 목록과 인용 목록이 다르면 결과를 거부한다. 의미 판단은 모델 검수의 책임이며, 인용이 존재한다는 사실만으로 의미가 맞다고 인증하지 않는다.

등록되지 않은 사실은 `claimId:null`로 추출한 뒤 서버에서 `unregistered:카드:필드:위치` ID를 붙인다. 해당 카드에 문제를 남겨 Claim 등록·근거 연결 후 다시 검사하게 한다. 누락된 필드, 연결되지 않은 평가, 위조 인용, 버전 불일치, 눈에 띄는 미분리 복합 주장 등은 검수 완료로 처리하지 않는다.

fixture의 평가는 저장된 공식 문구와 제한된 동일 의미 문구를 비교하는 보수적인 규칙 결과다. 모든 평가 이유에 fixture라고 표시한다. 이는 실제 모델의 원자 추출 성능 측정값이 아니다.

## 호출 기록과 비용

`callModel`을 통과하는 판단·작성·검수·평가 호출은 숨은 재시도 없이 다음 순서를 따른다.

1. 설정과 모델 호출 수·비용 상한을 확인한다. 부족하면 네트워크를 호출하지 않는다.
2. 입력량의 보수적 상한과 출력 토큰 상한으로 비용을 예약하고, `ModelCallRecord.status=reserved` 및 누적 사용량을 저장한다.
3. 실제 `fetch` 진입을 기준으로 `execution.apiCalls`를 증가시켜 저장한다. 설정값이 존재하는 것만으로 API를 호출했다고 표시하지 않는다.
4. 응답의 입력·출력 토큰 사용량으로 비용을 정산하여 먼저 저장한다.
5. 거절·출력 잘림·JSON·스키마 오류를 확인하고 성공 또는 실패 상태를 다시 저장한다.

사용량을 받지 못한 실패는 예약 비용을 유지한다. 정상 응답 뒤 파싱에 실패해도 이미 발생한 비용을 지우지 않는다. 재시작과 취소 복구는 실행 계층에서 이 원장을 유지한다.

개별 기록에는 호출 ID·시각·모델·프롬프트 버전·상태·예약액·정산액·토큰 수·제한된 오류 설명만 저장한다. API 키, 요청 헤더, 사용자 입력 전문, system 프롬프트 전문, 공급자 오류 본문은 호출 로그에 넣지 않는다.

## 검증 범위

`tests/verifier.test.ts`는 전체 필드 누락, 일부 문장 누락, 복합 주장 분리, 상상 속 사실, 잘못 연결된 출처, 인용 위조, 상반된 원자 판정과 fixture 표시를 검증한다. `tests/provider.test.ts`는 호출 전 예약 저장, 실제 fetch 계수, 정산 이후 실패, 로그의 비밀값 배제와 버전·검색 계약을 검증한다.

이 테스트들은 스키마와 실행 계약의 검증이다. 실제 모델의 의미 판단 정확도는 별도로 분리한 평가 자료와 사람이 확인한 정답으로 측정해야 한다.
